# SmartControl 安全与上线方案（BYOS 版）

> **产品形态已确认：BYOS（Bring Your Own Server）** —— 用户自己搭建 MQTT 服务，
> 在小程序「设置」页填入自己的服务器地址 + 用户名 + 密码。本项目**不提供后端服务**。
>
> 这份文档替代了早先的「多租户 + 后端签发临时凭证」方案。那套方案的前提
> （你运营一个公共 broker，需要按 openid 做租户隔离）在当前产品形态下**不成立**，
> 已全部作废。

---

## 一、为什么原方案作废

原方案要解决的是「多租户共用你的 broker，如何隔离」。但 BYOS 模型下：

| 原方案的假设 | BYOS 下的实际情况 |
|---|---|
| 用户都连你的公共 broker | 每个用户连**自己**的 broker |
| `device/#` 会订阅到别人的设备 | 订阅到的都是用户自己的设备 |
| 需要 openid 做租户隔离 | 没有租户概念，用户名密码本来就只对自己服务器有效 |
| 需要后端签发临时凭证 | 用户自己设密码，没有可签发的中央权威 |
| 需要 `%u` 占位符 ACL | 单用户场景下 ACL 价值有限 |

**结论：原方案的 90% 内容不适用。** 你关掉匿名（`allow_anonymous false`）
这个判断在当前架构下是**正确且充分**的——因为它挡住的正是"完全无凭据的陌生人"
这一类攻击者，而这正是 BYOS 场景下唯一的外部威胁。

---

## 二、关掉匿名后的实际安全态势

### 已经防住的
- ✅ 无凭据的扫描脚本直接连接 → 被 broker 拒绝
- ✅ 陌生人误打误撞连上 → 拒绝

### 仍然存在的风险（需要在文档/引导里警示用户）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **弱密码爆破** | 公网暴露的 MQTT 端口 7×24 被扫，弱密码会被撞开 | 强制提示用强密码；建议只在 CF Tunnel 后暴露 wss |
| **明文传输** | 若用 `ws://` 而非 `wss://`，密码在网络中是明文 | 只支持 wss；README 明确要求 |
| **本地凭据泄露** | 小程序 Storage 是明文，root/越狱设备或开发者工具可见 | 设置页已提示"勿在公用设备使用" |
| **同服务器多用户** | 若一个用户把服务分享给家人共用同一账号，则彼此可见全部设备 | 属用户自行决定；文档说明 |

> **⚠️ 最重要的一条**：MQTT over WebSocket **在 TLS 之前不做任何内容加密**（协议特性，非 bug）。
> 所以 `wss://` 是硬要求，`ws://` 等价于明文广播密码。README 与设置页都已标注。

## 三、用户自建 MQTT 服务的最小配置

给用户抄的 `mosquitto.conf`（**关匿名 + 强密码 + WebSocket + 只绑本地**）：

```conf
# ===== 认证：必开 =====
allow_anonymous false
password_file /mosquitto/config/passwd
per_listener_settings false

# ===== 内部监听：设备 TCP（ESP8266 走这里）=====
listener 1883
protocol mqtt
# 设备在局域网内连，无需绑定 0.0.0.0 暴露到公网

# ===== WebSocket 监听：给小程序用 =====
listener 9003
protocol websockets
bind_address 127.0.0.1      # ★ 关键：只绑本地，由 CF Tunnel 转发进来
```

创建账号（**不要在命令行用 `-p` 传密码**，会进入 shell 历史与 `ps` 输出）：

```bash
# 交互式输入密码
mosquitto_passwd -c /mosquitto/config/passwd youruser
# 追加第二个用户时去掉 -c（-c 会覆盖整个文件）
mosquitto_passwd /mosquitto/config/passwd youruser2
```

> **常见坑**：`mosquitto_passwd -c` 会**清空并重建**整个密码文件。
> 加第二个用户时必须去掉 `-c`，否则第一个用户会被删掉，表现为
> "之前能连的设备突然认证失败"。

然后 CF Tunnel 指到 `http://127.0.0.1:9003`，小程序填 `wss://你的域名`。

## 四、小程序端已完成的安全加固

本轮复查中已落地的改动：

### 4.1 强制账密（`pages/settings`）
关匿名后账密是必填项。若用户不填就点连接，会**一直卡在"用户名或密码错误"**，
而在 BYOS 场景下用户极可能误判成"服务器坏了"或"网络问题"，排查成本极高。

现在：
- 用户名/密码为空时直接弹窗提示"服务端已关闭匿名连接，必须填写用户名和密码"
- 设置页 tip 第 5 条明确写出 `allow_anonymous false` 这个关键词
- 新增第 8 条提示：公网暴露的 broker 会持续被扫描，务必用强密码

### 4.2 密码可见性切换
原来密码框是纯 `password` 掩码，用户输错一个字符要全部重打。
现在加了「显示 / 隐藏」切换（`showPass`），默认仍掩码。

### 4.3 致命错误常驻展示
账密错误（CONNACK rc=4/5）此前只有一条转瞬即逝的 toast，用户没看清就没了。
现在：
- `app.js` 把 `fatalReason` 存进 `globalData`
- 设置页顶部**常驻**一条红色提示："连接被服务器拒绝：用户名或密码错误。请检查下方用户名与密码。"
- 同时 `mqtt.js` 记录 `lastFatalReason`，且**不再自动重连**（账密错误重试一万次也不会好）

### 4.4 错误提示区分
| 场景 | 现在的提示 |
|---|---|
| 未连接就下发指令 | "未连接服务器，指令未发送" |
| 设备类型未知导致 topic 非法 | "设备类型异常，无法下发指令" |
| 账密错误 | "服务器拒绝：用户名或密码错误"（常驻） |

## 五、BYOS 模式的产品代价（需要正视）

这是比技术问题更影响"快速上线获得用户"的一件事：

**用户要自己完成这些步骤才能用起来：**

1. 搭一个 Mosquitto（Docker 或裸机）
2. 配 `password_file` 创建账号
3. 开 WebSocket 监听
4. 绑定域名
5. 配 TLS 证书
6. 装并配置 Cloudflare Tunnel
7. 在小程序「服务器域名」里报备 wss 合法域名（**这一步只有你自己能做**）

**能独立走完这套流程的用户比例很低。** 这是 BYOS 的结构性损耗，不是 bug。

### 现实的可能路径

| 阶段 | 做法 | 适用 |
|---|---|---|
| **当前** | 纯 BYOS，用户自己搭 | 你自己、以及懂技术的早期用户 |
| **可选增强** | 提供「一键部署」脚本（docker-compose + CF Tunnel 配置模板） | 把 7 步压缩成 2 步 |
| **长期** | 提供托管服务（此时原方案文档才重新适用） | 面向普通用户 |

**建议**：先把「一键部署脚本 + 图文教程」做出来，这是投入产出比最高的一步。
它能把你自己的部署经验固化下来，把用户的 7 步压到 2 步（跑脚本 + 填地址）。

## 六、上线前必须完成的合规项

无论 BYOS 还是托管，这几项都绕不开：

1. **服务器域名报备**
   小程序**不能**让用户填任意域名就连。必须在微信公众平台「开发 → 服务器域名 →
   WebSocket 合法域名」里加入域名。**未报备的域名在正式版会被直接拦截。**

   > ⚠️ **这是 BYOS 模式最大的矛盾点**：合法域名是**你**在小程序后台配置的，
   > 用户自己搭的服务如果域名不在白名单里，正式版**连不上**。
   > 开发版可以勾"不校验合法域名"绕过，但正式版不行。
   >
   > **可行做法**：
   > - 让用户把服务挂在一个**你已报备的泛域名**下（如 `*.yourdomain.com`），
   >   你提供 CF Tunnel 的 CNAME 指引
   > - 或者定位为「开发者自用 / 内测工具」，长期停留在体验版
   > - 或者转托管模式

2. **隐私协议**：调用 `wx.login` 需在「用户隐私保护指引」中声明（若后续加登录）；
   当前不收集任何用户数据，但仍需有隐私政策页面。

3. **《隐私政策》页面**：首次启动需用户同意。

4. **不得诱导分享 / 不得绕过审核**：BYOS 类工具容易被判"功能不完整"，
   提交审核时需说明"需配合用户自建服务使用"。

## 七、当前代码状态

本轮复查修复的问题（已通过 47 条 Node 桩测试 + 全文件语法校验）：

### 严重
- **旧 socket 回调解绑不彻底**：`closeTask()` 解绑了回调，但已进入事件队列的
  `onClose` 仍会在新连接建立后执行，把 `mqttTask` 置空 + 误排重连 →
  **表现为"刚连上就断开重连"的抖动**。已改为**连接代次号（`_connToken`）**机制，
  过期回调直接丢弃。

- **心跳定时器在断线路径未清理**：`onError`/`onClose` 里没调 `stopKeepAlive()`，
  残留的定时器会继续跑并判定"连接死亡"，造成重复重连。已补。

- **状态重复广播**：`globalData.setStatus` 不做去重，配合 `watchStatus` 注册时的
  立即回调，同一状态会连推多次，每个页面都多做一次 `setData`。已加去重 +
  初始化路径的 `force` 参数保证首帧仍能写入。

- **`subscribe()` 重复注册**：同一 path 反复订阅会累积条目，`handlePublish`
  逐条命中导致**同一回调被调用 N 次**。已加 `(path, cb)` 去重。

### 中等
- **MAC 校验过松**（只查长度 ≥ 6）：8 位或含非法字符的 MAC 能添加成功，
  但**永远离线且点了没反应**，极难排查。已收紧为 12 位十六进制，添加页给出明确提示。
- **`loadStore` 未去重 / 未排序**：脏数据可能含重复 MAC 与乱序 `sort`，
  导致列表重复行、改名只作用于第一条。已重写为过滤 + 去重 + 排序 + 连续编号。
- **`remove()` 未清理离线状态**：删设备后 `onlineMap` 残留，重新添加同一 MAC
  会**瞬间显示在线**（其实是上次的残留）。已清理。
- **`setOnline` 每次广播**：设备周期重发 `availability=1` 会反复 `fire()` 触发整表重绘。
  已加"无变化不广播"。
- **`availability` 重复帧推给页面**：控制页对 availability 是独立 `setData`，
  重复帧造成无谓渲染。现在只在状态**翻转**时才推。
- **`publish()` 的 `send` 未包 try**：socket 进入关闭流程但 `status` 未同步时
  `send` 会抛异常 —— 原来会让整个函数抛出，现在捕获并返回 `false`，
  避免调用方基于"成功"做乐观 UI 更新。
- **`requestState` 的 `task_` 字段解析重复两遍**：`parseState` 先探测变化、
  再写入，遍历了两次。已合并为一轮（`mergedTasks` 先组装再比对），
  并抽出 `_isFullTask()` 统一字段完整性判定。

### 轻微
- `device-add` 的 `typeZone` 未在 `data` 中声明 → 已补
- `device-add` 的 `onTypeChange` 未做越界校验 → 已补
- 列表页下拉刷新只是重绘缓存、不发查询，与顶部"刷新"按钮行为不一致 → 已对齐
- 详情页 `onPlugName` 缺 dataset 越界校验 → 已补
- `sendSubscribeNow` 无订阅项时会发空 SUBSCRIBE（部分 broker 会断开）→ 已拦
